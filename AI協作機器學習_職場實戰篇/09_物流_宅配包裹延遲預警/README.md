## 💡 為什麼採用「程式儲存格 ＋ AI 互動儲存格」的設計？

物流營運人員在學習機器學習時，最常遇到兩大困擾：
1. 完全讓 AI 從無到有自由寫程式，常因模型隨機性、套件版號衝突或語法報錯，導致學習卡關挫折。
2. 傳統程式教材只有代碼，沒有人解釋「為什麼物流時效管理要這樣做」。

因此，本範例採用了最穩健的高品質學習架構：
1. **保證可執行的穩定基底**：我們已經在 [宅配包裹延遲預警_分類篇.ipynb](./宅配包裹延遲預警_分類篇.ipynb) 中為你依序寫好了標準的機器學習程式儲存格（經過完整測試，絕無語法報錯）。
2. **段段有解說**：每個程式儲存格的**正下方**，都緊接著一個專屬的文字儲存格，以物流調度白話詳細說明「這段程式在做什麼」。
3. **內建豐富的 AI 伴學對話小抄 (Prompt)**：每個步驟依據非工程師應該掌握的核心觀念，提供多個不同角度的提問提示詞（包含雙11爆倉應變、天候降雨係數、SLA 違約賠付與程式碼客製修改），你可以自由挑選並複製貼給 Copilot / ChatGPT！

## 📊 資料集介紹 (`logistics.csv`)

📥 **資料集位置**：本機相對路徑 [`logistics.csv`](./logistics.csv)

本數據集記錄了宅配物流 2,000 件在途包裹的規格、轉運站狀態與最終配送時效結果：

| 欄位名稱 | 數據型態 | 數值範例 / 類別 | 物流運輸業務實務意涵 |
| :--- | :--- | :--- | :--- |
| **起運區域** | 類別型 (`object`) | 林口、台中、高雄轉運中心 | 包裹發貨總倉地點 |

| **包裹重量_kg** | 數值型 (`float64`) | 8.5 (kg，範圍 0.2~30 kg) | 影響裝載與搬運速度之重量 |
| **包裝材積大小** | 類別型 (`object`) | 小材積、中材積、大材積、超大材積 | 佔用貨車板位空間 |
| **出貨時間帶** | 類別型 (`object`) | 晨間批次、午後批次、傍晚夜配批次 | 出發時段與路況尖峰關聯 |
| **當日轉運站包裹總量** | 數值型 (`int64`) | 68,000 (件) | 站所分揀與出貨負載壓力 |
| **降雨強度** | 類別型 (`object`) | 無雨/晴朗、局部陣雨、大雨滂沱/暴雨 | 行車安全速度與延誤主因 |
| **是否為大促檔期** | 類別型 (`object`) | 是、否 | 電商大檔期爆倉指標 |
| **配送是否延遲 (目標 y)** | 類別型 (`object`) | **「是」 / 「否」** | **預測目標變數（二元分類）** |

## 🖥️ 進階專題：餵資料給 AI，打造獨立桌面預測 App (`app.py`)

在真實物流調度中，你不需要把整個 `ipynb` 的代碼全部搬過去。當你掌握了基本觀念後，你可以**直接把手邊的在途包裹與站所資料結構餵給 AI**，讓 AI 替你撰寫獨立運作的桌面視窗預警工具 (`app.py`)。

但是，**新手最忌諱讓 AI「自作主張、一口氣吐出整份代碼」**，因為那樣你根本不知道 AI 擅自做了哪些假設。

因此，我們設計了這份**「優良的伴學諮詢式 Prompt」**：
- 它強制 AI 扮演**耐心的技術顧問**，嚴禁直接噴出程式碼！
- 當 AI 遇到重要的機器學習決策時，**必須主動用白話詢問你，而且每次提問都必須先向你解釋：「為什麼我身為 AI 必須這樣問你？這在機器學習代表什麼意思？」**
- 透過一問一答，你既能釐清物流調度需求，又能理解模型設計本質，最後產出完美的桌面 App！

### 📋 複製給 AI 的專屬【新手伴學諮詢 Prompt】

```text
你是一位專為「零程式背景、剛接觸機器學習的物流行控主管/調度員」服務的資深 AI 機器學習架構師與導師。

我現在手邊有一份資料集，我希望最終由你為我寫出一個單一、獨立、開箱即用的 Python 桌面視窗應用程式（`app.py`，使用 Python 內建的 Tkinter 或 PyQt）。

【我的物流資料說明】
資料檔案：`logistics.csv`（宅配包裹在途環境與延遲紀錄）
資料欄位如下：
- 起運區域（北部轉運中心(林口)、中部轉運中心(台中)、南部轉運中心(高雄)）
- 配送行政區（台北市都會區、新北市偏遠山區、台中市都會區、高雄市都會區、花蓮台東花東線）
- 包裹重量_kg（數值型，0.5~30 kg）
- 包裝材積大小（小材積、中材積、大材積、超大材積）
- 出貨時間帶（晨間批次、午後批次、傍晚夜配批次）
- 當日轉運站包裹總量（數值型，15,000~85,000 件）
- 降雨強度（無雨/晴朗、局部陣雨、大雨滂沱/暴雨）
- 是否為大促檔期（是、否）
- 配送是否延遲（是、否）

⚠️【極度重要規則：請絕對不要直接給我程式碼！】
因為我是機器學習新手，如果你直接給我整份程式碼，我無法理解背後的決策邏輯。
在動手寫程式碼之前，請你扮演「親切耐心的專業顧問」，依序向我確認關鍵問題。
並且，**你提出每一個問題時，都必須嚴格遵循以下「解說式提問格式」向我說明**：

--------------------------------------------------
【提問格式規範】
👉 問題 X：[你要問我的具體問題]
💡【為什麼我要這樣問你？（大白話解釋）】：[請用生活化白話向非工程師說明：為什麼演算法無法自己決定這件事？背後的資料科學原因是什麼？]
📌【建議選項與物流影響】：
   - 選項 A：...（說明若選此項，在物流調度或模型上的影響）
   - 選項 B：...（說明若選此項，在物流調度或模型上的影響）
--------------------------------------------------

請針對以下四個核心面向逐一向我提問，並附上白話解釋：

1. 【確認預測目標 Target / y】
   - 請告訴我：為什麼機器學習演算法分不出誰是「路況與站所負荷原因（特徵）」、誰是「我們要預警的結果（是否延遲）」？
2. 【檢查是否有作弊欄位或妥投後的資訊】
   - 請告訴我：為什麼如果把「收件人簽收時間」或「司機延遲回報原因」放進去訓練，會造成嚴重的「資料洩漏（偷看答案）」？
3. 【權衡延遲客訴與調度成本（Precision vs. Recall）】
   - 請告訴我：「漏抓了真正會延遲的件導致大客戶客訴索賠（漏報）」，與「把可以準時送達的件誤判為高風險而多派外包專車支援（誤報）」，這在統計指標上對應什麼？在物流營運上該如何拿捏？
4. 【桌面 App 的操作體驗與防呆設計】
   - 請告訴我：既然是給行控中心調度人員在出車前使用，為什麼介面必須內建「快速預測範例情境按鈕」？以及評估結果該如何提供加派專車或通知客戶的具體指引？

請立刻開始扮演顧問向我提問，等待我的回覆後，才進行 `app.py` 的程式碼撰寫！
```
